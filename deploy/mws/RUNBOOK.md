# RUNBOOK — эксплуатация Live-инфраструктуры MWS

Операционный справочник для фазы L5a (провижининг) и связанных с ней ручных
процедур (L5c: восстановление, ротация ключей). Архитектурная основа —
docs/GENESIS_LIVE.md §7 и §10. Этот документ не переопределяет условия
перехода фазы — он описывает, как их выполнить, когда владелец подтвердит
список ресурсов.

## 1. `provision.sh`: что он делает и почему он остановится сам

`deploy/mws/provision.sh` создаёт (в этом порядке): сервисные аккаунты и
ключи IAM → пустые контейнеры секретов Secret Manager → сеть/подсеть/
внешний адрес/firewall VPC → диски и VM `anu-live-1` → реестр образов.

Условие перехода фазы L5a в docs/GENESIS_LIVE.md требует, чтобы владелец
**сначала подтвердил список ресурсов**, а затем **лично** выполнил шаг с
секретами и IAM-биндингами (CLI `mws` этого не умеет). Поэтому скрипт
встроил это условие в код, а не оставил его только текстом:

- без флага `--yes-i-understand-this-costs-real-money` и без интерактивного
  ответа `y` на явный вопрос скрипт завершается кодом 1 **до** первого
  вызова `mws`, создающего что-либо;
- без переменной `OWNER_SSH_IP` скрипт падает ещё раньше — она нужна
  правилу `ssh-from-owner`.

Перед реальным запуском:

1. Свериться с квотами проекта `project-vxgxs2` в консоли/поддержке MWS.
   Более ранняя попытка (см. заголовок provision.sh) упёрлась в исчерпанные
   vCPU, суммарный размер дисков `nbs-pl2` и внешние адреса — без запаса по
   квоте реальные вызовы провалятся так же.
2. Прочитать целиком банер, который печатает сам скрипт перед вопросом —
   он перечисляет каждый ресурс, который будет создан.
3. Ответить `y` (или передать флаг для неинтерактивного запуска — например,
   из CI с ручным approval-гейтом снаружи, не автоматически).

## 2. IAM role bindings — ручной чеклист (консоль MWS/REST)

`mws iam role` в CLI — только `get`/`list`, привязка ролей недоступна из
командной строки (подтверждено `mws iam role --help`). После того как
`provision.sh` создал сервисные аккаунты, назначьте в консоли MWS (или через
REST API) вручную:

- [ ] `anu-live` → чтение секретов `anu-live-*` в Secret Manager
- [ ] `anu-live` → pull из `registry/projects/project-vxgxs2/registries/anu`
- [ ] `anu-live` → `compute disk-backup create` на диск `anu-live-evidence-01`
- [ ] `anu-anchor` → запись в S3-бакет `anu-live-anchors` — **и только туда**
      (не давайте этому SA ничего сверх записи в этот один бакет)

Проверка после назначения (все — команды чтения/безопасные для повторного
запуска, но `disk-backup create` создаёт реальную резервную копию, поэтому
её не гонять "на пробу" — только `list`):

```bash
mws --impersonate iam/projects/project-vxgxs2/serviceAccounts/anu-live \
    secretmanager secret-version get-data --name anu-live-provider-key -f json

mws --impersonate iam/projects/project-vxgxs2/serviceAccounts/anu-live \
    compute disk-backup list -f json

# docker pull под профилем VM (не impersonate с Lab — реальная проверка
# доступа к реестру делается с самой VM, где установлен authorized key SA anu-live)
```

S3-запись под `anu-anchor` проверяется запуском `deploy/mws/s3-bucket.sh`
(создаёт/подтверждает бакет и его versioning под HMAC-ключом `anchors`).

## 3. Секреты — кто их создаёт и когда

`provision.sh` создаёт только пустые контейнеры (`secretmanager secret
create --active`, без данных). Версии с реальными значениями создаёт
**владелец вручную**:

```bash
# Формат ввода данных версии секрета — сверить при первом реальном запуске
# (см. §8 docs/GENESIS_LIVE.md); ниже — заведомо НЕ финальная команда, а
# место, где она появится после подтверждения формата.
mws secretmanager secret-version create secretmanager/projects/project-vxgxs2/secrets/anu-live-provider-key/secretVersions/1 ...
```

После этого на VM `anu-secrets.service` (см. `deploy/mws/anu-secrets.sh`)
читает все три секрета в tmpfs `/run/anu/secrets/` при каждом запуске —
значения никогда не попадают на персистентный диск и не логируются.

Реестр всех ключей, где они хранятся и как их ротировать — `KEYS.md`.

## 4. Аварийная остановка

```bash
mws iam api-key update "iam/projects/project-vxgxs2/serviceAccounts/anu-live/apiKeys/anu-live-inference" --active=false
```

Деактивация ключа провайдера не трогает саму VM, контейнеры или супервизор
напрямую — она обрывает ответы шлюза. Супервизор (`anu lab live`, фаза
L3c, `src/lab/live/supervisor.ts`) считает подряд идущие тики без
полученного ответа (`--outage-ticks`, по умолчанию — заданное при запуске
значение, пример из справки команды — 3) и **ставит вселенную на паузу на
границе тика**, а не обрывает её в середине — это то же поведение, что и
штатная остановка контейнера (`SIGINT`/`SIGTERM`), только без перезапуска.
Возобновление — обратная команда:

```bash
mws iam api-key update "iam/projects/project-vxgxs2/serviceAccounts/anu-live/apiKeys/anu-live-inference" --active
```

и перезапуск контейнера движка (не самого ключа — активация ключа не
пробуждает уже остановленный процесс сама по себе).

## 5. Restore-drill

`deploy/mws/restore-drill.sh` — учебное восстановление из последнего
`disk-backup`. Выбранный подход и почему он не трогает саму `anu-live-1` —
в заголовке скрипта. Коротко: одноразовая scratch-VM без внешнего адреса,
доступная по SSH только с самой `anu-live-1`, все временные ресурсы
удаляются в конце запуска (`trap cleanup EXIT`), тем же предохранителем,
что и `provision.sh`.

Известный пробел: архитектурный документ ссылается на
`anu lab replay --allow-incomplete-boundary`, которого в реальном CLI нет
(см. `src/lab/runner.ts`, `REPLAY_OPTIONS`) — скрипт использует только
реально существующие флаги и печатает это как явный, задокументированный
пробел, а не выдуманный флаг. Библиотечный метод с допуском
`allowIncompleteBoundary` существует (`src/lab/replay.ts`,
`ReplayEngine.replayRecoverableFile`), но не прокинут в CLI — это отдельная
задача для инструментария, не для этого раннбука.

Результат каждого прогона (успех / частичный успех — граница тика

## 6. Ротация ключей

Процедура по каждой строке `KEYS.md` — там же и колонка "Ротация" с точным
шагом. Общий паттерн для ключей в Secret Manager (провайдер, шлюз,
Observer): новая версия секрета → `systemctl restart anu-secrets` на VM →
рестарт только того контейнера, который держит этот секрет (не всего
стека — `anu-secrets.service` сам по себе не рестартует ничего, кроме
собственного чтения секретов в tmpfs).

Для ключа сайта Ask Lab (SA `xteam-pro`, истекает 2026-11-22) — замена на
`anu-site-ask/ask-lab` до срока, отдельно от остальной ротации: правится
`.env` сайта StudyLabPro, не эта VM.

Grafana-алерт «ключ истекает» по каждой строке `KEYS.md` — не входит в
объём L5a (см. TODO в `KEYS.md`), задача фазы L5c.
